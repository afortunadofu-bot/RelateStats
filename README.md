# RelateStats

Android 社交數據記錄 App。不 root、不碰任何資料庫，只靠 **通知監聽** 與 **無障礙服務** 兩個引擎，
統計你在通訊軟體上對每個人投入的「注意力停留時間」與「互動頻率」，並做社交人格與數位健康分析。

- **目前版本**：v2.1（versionCode 11）
- **技術棧**：Kotlin + Jetpack Compose + ViewModel / StateFlow
- **資料儲存**：全本地 SharedPreferences（`RelateStatsData`），不上傳任何伺服器
- **原始規劃**：[docs/BLUEPRINT.md](docs/BLUEPRINT.md)
- **完整修復與變更紀錄**：[docs/CHANGELOG.md](docs/CHANGELOG.md)
- **上架 Google Play 規劃**：[docs/PLAY_STORE_PLAN.md](docs/PLAY_STORE_PLAN.md)
- **Play Console 送審資料（可直接貼上）**：[docs/play/SUBMISSION.md](docs/play/SUBMISSION.md)
- **隱私權政策**：[docs/privacy-policy.html](docs/privacy-policy.html)

### ⚠️ 上架相關的硬規則

- **`applicationId = com.relatestats.app` 第一次上傳後永遠不能改。**
- **不要加 `INTERNET` 權限。** 「資料傳不出手機」是隱私權政策、資料安全性表單、無障礙聲明的共同前提，加了三份都要重寫。
  雲端備份因此走系統檔案選擇器（SAF），上傳交給雲端硬碟 App，而不是 Google 登入＋Drive API。
- **不要加 `READ_CALL_LOG`**（受限權限）。
- 雲端備份位置只存「提供者＋檔名」（SAF 拿不到資料夾路徑），**在綁定當下算好存起來**，不要每次開設定頁去查雲端硬碟。
- 雲端備份週期由每晚回顧鬧鐘檢查，比對時容許 3 小時誤差（鬧鐘有一小時的窗），否則每天備份會常常變成隔天。
- **所有開權限的入口都要先經過 `PermissionDisclosureDialog`**，不能直接 `startActivity` 到系統設定頁（Play 明確揭露規定）。
- **四份文字要一致**：`PermissionDisclosureDialog`、`strings.xml` 的 `accessibility_desc`、`docs/privacy-policy.html`、`docs/play/SUBMISSION.md`。改一份就四份一起改。
- **`keystore.properties` 與 `.jks` 絕不能 commit**（已列入 `.gitignore`）。
- 備份規則 xml 只 include 一個檔，**不要再加 exclude**，否則 release lint 會判致命錯誤。

## 快速開始

在 Android Studio 直接按 Run 即可。若要用命令列建置，**這台機器的 `java` 不在 PATH**，必須先指定 `JAVA_HOME`：

```bash
$env:JAVA_HOME="C:\Program Files\Android\Android Studio\jbr"; .\gradlew.bat assembleDebug
```

產出的 APK 在 `app/build/outputs/apk/debug/app-debug.apk`。

安裝到實機：

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

首次安裝後必須到 **設定分頁** 手動開啟三項權限，否則不會有任何數據：

| 權限 | 用途 | 沒開會怎樣 |
|---|---|---|
| 通知存取 | 攔截訊息、計算字數與訊息量 | 完全沒有訊息紀錄 |
| 無障礙服務 | 計算聊天室真實停留時間 | 停留時間全部是 0 |
| 使用紀錄存取 | 讀取手機總螢幕時間，算佔比 | 佔比分析不顯示 |

> Samsung 等機型若在系統設定裡找不到本 App，需先到「應用程式 → 本 App → 右上角 → 允許受限制的設定」。

> ⚠️ **每次重新安裝 App，Android 都會自動關閉無障礙服務與通知存取**，這是系統行為。
> 更新後務必回設定頁重新開啟，否則不會記錄任何新資料。App 內會顯示紅色警示橫幅提醒。

## 目前功能

**五大分頁**

- **總覽**：KPI 四格、人格條、平台分佈、標籤分佈、時段分佈、互動對象 Top 5、活躍熱力圖、常用詞
- **排行**：表格式排行列，篩選器收合在「篩選」按鈕內，可勾選批次設定標籤，點列看 24 小時活躍分析與群組發言排行
- **洞察**：期間對比、逐日趨勢、活躍密度、覆蓋率與連續天數、社交集中度（基尼係數）、群組 vs 個人、深夜社交指數、通話統計、訊息長度分佈、連續互動排行、跨平台聯絡、新增與沉寂聯絡人
- **聯絡人**：跨平台帳號合併（可搜尋、可自動合併相似）、多選批次分組、依平台篩選、垃圾聯絡人一鍵清除
- **設定**：權限監測、標籤管理、一週起始日、備份還原、資料管理

**資料管理**

- 一鍵清除垃圾聯絡人（讚／追蹤者／串文推播等非真人通知）
- 逐筆檢視／勾選刪除紀錄
- **所有刪除操作皆可復原**（設定頁「資料管理」）
- 多選批次設定標籤與刪除
- 清除今日／本週／指定日期／全部
- 自動清理異常紀錄（升級時執行一次）

**標籤**

預設 家人／伴侶／朋友／工作／未分類／系統通知，全部可改名、換色、排序、刪除、新增。

**備份**

- Android 自動備份（綁定手機的 Google 帳號，換機自動還原）
- 分享備份檔到 Google 雲端硬碟 / LINE Keep / Gmail（走系統分享選單）
- 匯出成檔案 / 選擇檔案還原

## ⚠️ 注意事項

### 資料相關

- **所有資料只存在這支手機**，沒有伺服器。換機或重灌前務必先備份。
- **v1.1 以前累積的停留時間資料全部是錯的，且無法還原**。舊版把毫秒當秒存、碼錶又不會停，
  單筆紀錄出現過 999,000,000 秒（約 31 年）。升級到 v1.2 時會自動清掉這些異常紀錄
  （清理前會先另存原始資料到 App 內部空間）。**訊息數與字數的歷史資料是好的，不受影響。**
- **常用詞從 v1.3 才開始累積**。舊資料只存了字數沒存內容，無法回推。剛升級時這張卡是空的。
- 常用詞是**全期間累計**，不隨日期篩選變動；只存詞頻，不保留訊息原文。
- **訊息數與停留時間是互補的，不是同一件事**：進到聊天室閱讀時不會跳通知，
  所以訊息數反映「被動接收」、停留時間反映「主動開啟」，加起來才是完整的注意力。
  訊息數不需要無障礙服務就能取得，因此各處預設指標都是訊息數。
- 單筆紀錄上限 200,000 筆，超過會保留最新的。
- 單次聊天室停留上限 **1800 秒**（30 分鐘），超過視為背景掛機直接丟棄而非記成上限值。

### 列表的寫法

- **超過 20 筆的清單要有 `ListScrollbar` 與 `ScrollTopButton`**，兩個都需要 `LazyListState`。
  ⚠️ 捲動條的位置用「第幾筆」估算，不是像素 —— LazyColumn 的列高不一定一樣，
  要精確像素得把所有列都量過，那就失去 lazy 的意義。對「快速跳到中間」這個用途，索引估算夠準。
- `listState` 一律用 `rememberSaveable(saver = LazyListState.Saver)`，切出去再回來不要彈回最上面。

長清單（聯絡人、排行）**不要一人一張圓角外框卡**：
幾百張疊起來全是框線，長得像 AI 生的範例畫面。
改用銀行 App 的做法：**整份清單是一張白卡，列與列之間用細分隔線**，
首尾兩列才圓角（`LazyColumn` 的 `spacedBy` 要設 0，頭部卡片自己帶下方留白）。

### 大字體是常態，不是例外

使用者的系統字體約 **1.8 倍**。這代表：

- **一列裡不要放一排彩色膠囊**。9sp 放大後是 16sp，四顆膠囊直接撐爆父容器；
  `Row` 不裁切子元件，所以溢出的那顆會被卡片邊緣切掉。
  改成**一行灰字**（LINE · IG · Messenger），字再大也只是省略號。
- 圖示、膠囊、標籤這類陣列式的元件，數量要可控（take(n) + 「+N」）或改成可滾動。

### 使用說明

- **是整頁不是彈窗**（`UserGuideScreen`）。八個章節塞進 460dp 的 AlertDialog，
  大字體下一次只看得到一段，也看不到「總共有哪些主題」。
- ⚠️ **不要用「早退」的寫法把設定頁換掉**（`if (show) { Screen(); return }`）——
  早退等於整棵子樹被丟掉，回來時設定頁的捲動位置與所有本地狀態都會重置。
  正確做法是蓋在上面：說明頁自己有不透明底色，設定頁還在下面原封不動。
- 內容分兩區：**常見問題**（東西不對時怎麼辦，`USER_FAQ`）與 **運作原理**（`USER_GUIDE`），
  每段預設收合，展開狀態用 `rememberSaveable`。

- 內容在 `USER_GUIDE` 常數（`GuideSection` 清單），**資料與畫面分開**，
  要加一節只要往清單裡加一筆。
- 改到會影響使用者認知的行為時（新指標、時間範圍規則、權限），
  記得同步更新說明 —— 這個 App 有不少「為什麼是這樣」需要交代，
  看不到解釋使用者就會以為是算錯。

### 設定頁

整頁只用一組元件，新增任何東西都照這個規則走，不要再各寫各的：

| 元件 | 用途 |
|---|---|
| `SettingsCard` | 唯一的容器。Surface 底、1dp 邊框、14dp 圓角、無陰影 |
| `SettingsSection` | 區段小標（服務 / 偏好 / 備份 / 資料） |
| `SettingsRow` | 標準一列：標題 + 說明 + `›`。**說明是必填的** |
| `SettingsDivider` | 卡內分隔線，從文字起點開始不貼滿整張卡 |
| `PermissionRow` | 權限列，狀態用色點 + 短字的膠囊 |

- **`SettingsRow` 的說明不能省。** 只有標題的話，「整理系統通知」這種名字
  猜不出會發生什麼事，使用者就不敢按。
- 破壞性動作（清除資料、清除常用詞）用 `danger = true` 並排在該區最後。
- 字級只用 `T` 標尺；例外只有頁面主標 24sp 與 `›` 的 18sp。

### 手勢

- **左右滑動換上一期／下一期**（`Modifier.dateSwipe`）。
  ⚠️ 掛在**整頁的最外層容器**上，不是掛在日期列上 ——
  日期列的分頁鈕與箭頭都有自己的 `clickable`，會先吃掉手勢，滑起來時靈時不靈。
- 垂直捲動不受影響：`LazyColumn` 只消費垂直方向的拖曳，水平方向沒人消費才會冒泡上來。
  頁面內的 `horizontalScroll` 橫向清單（標籤列、平台列）會自己消費掉，滑那幾條不會誤觸換日期。
- 門檻 90px，不然直向捲動時手指稍微歪掉就換日期。「全部」與「區間」沒有上一期可言，直接不掛。

### 返回鍵

- **分頁有返回堆疊**（`MainAppContent` 的 `tabStack`）。沒有它，按實體返回鍵會直接退出 App。
- ⚠️ **不要改成「一律回概況」** —— 從排行→分析按返回會跳到概況，使用者要的是回到剛剛那一頁。
- 切到已在堆疊裡的分頁時先 `remove` 再 `add`，否則堆疊會長出一堆重複項，要按很多次才退得出去。
- 堆疊只剩一頁時 `BackHandler` 會關閉，返回鍵回歸系統預設（退出 App）——這是對的，不要擋。
- **多選模式中按返回＝取消多選**，不是離開頁面。聯絡人頁與排行頁各自有一個 `BackHandler(enabled = selectionMode)`，
  它會比分頁堆疊那個更早接到事件（巢狀較深者優先）。

### 配色

**中性色與強調色是兩套東西。**

- **中性色固定不動**：`Background` / `Surface` / `SurfaceAlt` / `Text*` / `Border*`。
  背景、卡片、文字、分隔線永遠是那套灰白 —— 不管選哪一組配色，App 都還是同一個 App。
- **強調色跟著配色走**：`BrandPrimary`（深色填充）與 `ActiveBlue`（連結／選中／高亮）
  都是 `ChartPalette` 的 `brand` / `accent`。
  ⚠️ v3.16 把它們寫死，結果選了粉色配色卻看到藍色的「本週」跟藍色分頁高亮，畫面整個是散的。
  第一組的 `accent` / `brand` 就等於原本的 #2563EB / #0F172A，所以預設值跟以前一模一樣。
- **資料色可設定**：`AppColors.Chart`（`ChartPalette`，5 組）。圓餅切片、長條、格子色階、比例條走這裡。
  ⚠️ **畫資料不要用 `ActiveBlue`**，要用 `AppColors.Chart.primary` / `.at(i)`。
- `colors[0]` 同時是單色圖表（長條圖、色階格子）的主色，所以每組的第一個都必須「單獨用也夠深」。
- **不進配色的兩種顏色**：
  - 標籤色（家人、同事…）—— 使用者自己挑的，覆蓋掉等於把設定弄丟。標籤圓餅維持用標籤色。
  - 「上升／下降」的綠紅（`AppColors.Positive`）—— 那是語意，不是裝飾。
- 平台圓餅**改吃配色而不是品牌色**：LINE 綠、IG 粉彼此明度差太大，湊成一張圖本來就不成套；
  平台名稱寫在圖例上，不靠顏色辨認。（聯絡人列上的平台標籤仍用品牌色，那是標籤不是圖表。）
- ⚠️ **`AppColors.Chart` 必須寫成 `get()` 並讀 `chartPaletteState`（Compose `MutableState`）**，
  不能改成普通 `var` —— 那樣換配色畫面不會重組。
- ⚠️ **`MaterialTheme` 一定要帶 `colorScheme`。** 空的 `MaterialTheme{}` 會整包吃 Material3 預設紫：
  導覽列選中膠囊、Checkbox、TextButton 文字、輸入框游標全是紫的。
  `appColorScheme()` 用的是**固定的**介面色，不跟著圖表配色變。
- **標籤色也吃這組配色。** 標籤與圖表是同一批資料的兩種呈現，配色分家會很怪。
- **五組莫蘭迪色盤**：A 霧灰藍、B 酒紅暖調、C 抹茶灰綠、D 大地棕調、E 山巒暮色。
- ⚠️ **`colors`（圖表 6 色）與 `tags`（標籤 7 組）是兩份獨立的資料，不互相衍生。**
  舊版是「text 壓到 15% 透明度當 bg」，同一組裡所有標籤的底色深淺會一模一樣，
  只剩文字色有差 —— 小 chip 上根本分不出來。現在 bg 與 text 都明寫，底色也刻意做出深淺差。
  兩者只要求**色相彼此呼應**，維持整組的一致感。
- **`tags` 的順序是固定的**：0 伴侶　1 家人　2 朋友　3 工作　4 其他　5 系統通知　6 未分類。
  `ContactCategory` 的 `colorInt` 存的就是這個索引。
- ⚠️ **索引 6（未分類）是 `dashed`：透明底＋虛線框。** 它代表「還沒分」，不該長得像一個真正的標籤。
  自訂標籤配色只開放 0–4，不然使用者會挑到一個看起來沒分類的樣式。
- ⚠️ **所有 chip 一律用 `Modifier.tagChip(cat, radius)`**，不要再各自寫 `.background(cat.bgColor, …)` ——
  虛線樣式是在那個 modifier 裡處理的，各寫各的一定會漏掉幾處。
- ⚠️ **改索引順序時要寫 migration。** v3.23 把順序重排，舊資料的「系統通知」停在索引 7，
  新的 tags 只有 0..6，取模後會拿到索引 0，系統通知就長得跟伴侶一模一樣（見 `migrateTagSlots`）。
- ⚠️ **`NavigationBar` 的 `tonalElevation` 必須是 0。**
  `containerColor` 跟 `colorScheme.surface` 相等時，M3 會拿 primary 疊一層色調膜上去，
  整條分頁列會變成淡藍／淡紫，跟白底的內容區對不起來。分隔靠上緣的細線。
- ⚠️ **`ChartPalette.tags` 必須跟 `colors` 分開列。** 標籤是「淺底＋深字」，
  圖表色裡那些很淺的（#CEDCE7 之類）拿來當字色根本看不見。
  `tags` 每一個都必須是白底上讀得清楚的深度；底色一律由字色壓到 15% 透明度得出，不另外列。
- ⚠️ **同色系配色不要照明度排序。** 相鄰兩塊在圓餅圖上會糊在一起，一律深、淺、深、淺交錯放。
- **`ContactCategory` 的 `colorInt` 有兩種意義**：`0..15` 是配色索引（跟著配色變），
  其他值是舊資料的絕對色值。真正的 ARGB 帶 alpha，轉成 Int 是負數，不會撞到 0..15。
  舊資料由 `migrateTagColorsToIndex()` 一次性轉換，
  ⚠️ 它**必須排在 `_availableCategories` 讀完之後** —— 放前面會對著空清單做轉換然後把旗標設成已完成。
  對不上舊色票的怪色保留原樣，不要硬塞索引。
- 新增一組配色只要往 `CHART_PALETTES` 加一筆，設定頁會自己長出來。
  設定頁**只顯示顏色不寫名字**，而且四組壓成一列色帶 —— 這只是偏好設定，不該比服務狀態顯眼。

### 圖表相關

- ⚠️ **甜甜圈中間的數字要用 `fitInHoleSp()` 縮字**，不要寫死 17sp。空心內徑只有約 65dp，
  「55123」「6h 57m」加上系統字體放大就會溢出圓環。
- ⚠️ **「幾點在聊」的星期標籤必須畫在同一張 Canvas 裡。** 拆成「左邊一欄 Box ＋ 右邊一張 Canvas」時，
  兩邊各自把 dp 換成 px 再四捨五入，七列累積下來就差好幾個像素。同一張 Canvas 共用列高才不可能對不齊。
- 「＋其他 N 項／位」必須是按得下去的按鈕（點了展開），不能只是灰字。
- logo 用固定色（#0F172A / #2563EB），**不跟著配色走**。
- 「活躍天數」區塊已移除：多數人天天都在聊，覆蓋率幾乎永遠接近 100%。

- ⚠️ **只有一個資料點時不要畫趨勢圖。** 一根長條寬度平分、高度必然 100%，
  結果就是一整塊色塊。「趨勢」本來就需要至少兩個點，`b.trend.size >= 2` 才建立區塊。
- ⚠️ **比例條某一邊是 0 時，那一邊也要留一截顏色（4%）。**
  寬度給 0 會讓那一邊整個消失，使用者分不出「這邊是 0」跟「這張圖沒畫出來」。
- 所有圖表的顏色（含時段分佈）一律走 `AppColors.Chart`，不要用寫死的 `st.color`。

- ⚠️ **「哪幾天在聊」與「幾點在聊」是兩張長得很像但問題完全不同的格子圖**，
  名稱必須直接寫出它回答什麼，否則第一次看只看得到兩片色塊：
  - 哪幾天在聊（`contrib`）＝看**日曆**。一格一天，橫向一欄是一週，近 17 週。
  - 幾點在聊（`heatmap`）＝看**時鐘**。一格是「星期幾的第幾個小時」，橫向是 0–23 點。
  兩張的 `InfoDot` 都要互相點名對方，講清楚差在哪。
- **格子圖一定要有三件事**：軸的意思（「每一欄＝一週」「小時」）、色階圖例（少→多，含最高值）、
  以及**不用操作就看得到的結論**。「幾點在聊」沒選格子時預設顯示尖峰時段，
  就是為了讓第一次看的人不必自己找最深的那一格。
- 說明文字塞進 `InfoDot`，軸與圖例則塞進**本來就存在的那一行**
  （圖例列左邊原本是空的），不要為了標示另外開新的一行小字。

### 版面相關

- ⚠️ **`Scaffold` 的內容不要再加 `navigationBarsPadding()`。**
  `paddingValues` 已經含了「導覽列高度 + 系統手勢列」的內距，
  再加一次等於多墊一條系統列的高度，中間就露出 Scaffold 的底色 —— 那條固定的灰帶就是這樣來的。

- **`DataRow` 是平台分佈、標籤分佈、訊息長度、Top 5、聯絡人詳情共用的**，
  改它的高度等於一次改掉全部清單。主／次數值請維持「同一行並排」，
  不要改回上下兩行 —— 兩行加上留白一列就要 ~39dp，五六列就吃掉半個螢幕。
- **一週起始日有三個地方要吃到同一個設定**：日期篩選的月曆、活躍密度、活躍熱力圖。
  漏掉任何一個，畫面上就會出現「本週從週一算、熱力圖從週日算」的矛盾。
  資料層一律以週日為索引 0，只有顯示時才旋轉。

- **不要對「裝著文字的容器」寫死 `.height(xx.dp)`**。容器是 dp、字是 sp，
  使用者把系統字體調大時字會變大、容器不會，結果就是被裁掉半行。
  同一列要等高，正確做法是外層 `Row(Modifier.height(IntrinsicSize.Min))` + 內層 `fillMaxHeight()`，
  讓整列跟著最高的那格一起長。
- 同理，中文文字**不要寫死 `lineHeight`**，字型自己的行高才含得下下緣（ㄅㄆ、口、日等字）。
- **`.width()` 有一模一樣的問題**。裝文字的欄位一律用 `widthIn(min = xx.dp)`，
  留最小寬度但允許長大。例外：若欄位內的子元件用了 `fillMaxWidth()`，
  就**必須**保留固定 `width()`，改成 `widthIn` 會讓子元件撐滿整列（貢獻格星期欄就是這個情況）。
- **兩兩並排的卡片，選填欄位要畫空字串而不是不畫**。一格有副標、另一格沒有，
  高度就會差一行，看起來就是跑版（`StatPair` 踩過）。
- 純圖形的方塊（進度條、長條圖畫布）寫死 dp 是**正確的**，裡面沒有 sp 文字就不受字體縮放影響。
- ⚠️ **`InfoDot` 的 ⓘ 不可以寫死 `size()`**。以前是 20dp 的圓框裝 13sp 的字，字體放大後 ⓘ 被切掉一半。
  現在讓框跟著字長，點擊範圍靠 `padding` 撐開。任何「圓框裝一個字」的元件都適用這條。
- **提醒卡一律用 `NoticeCard`，不要再寫「整塊粉紅底 + 兩顆整寬紅按鈕」。**
  那是警告等級的視覺語言，但這些多半只是待辦提醒，滿版紅色會讓整頁看起來像 App 壞了。
  `NoticeCard` = 白底卡 + 左側細色帶 + `NoticeAction` 文字型動作；填色只留給主要動作。
  左色帶用 `height(IntrinsicSize.Min)` + `fillMaxHeight()`，不要寫死高度。
- **不要為了一顆按鈕開一整列**。一頁只有一顆的入口（洞察頁「排序」就是），
  自己站一列等於整列都是空的，大字體下更浪費。
  `StickyDateBar` / `TimeFilterSelector` 留了一個 `trailing` 插槽，
  按鈕畫在「單日／單週／區間／全部」那一列的右邊，不吃任何額外垂直空間。
  ⚠️ 插槽刻意放在**分頁列**而不是「‹ 日期 ›」那一列 —— 選「全部」時後者根本不會出現，按鈕會跟著消失。
  插槽內的按鈕請用 `fillMaxHeight()`（外層已經是 `height(IntrinsicSize.Min)`），不要寫死高度。

### 效能相關（閃退的主因）

- **`isNonPersonContact()` 是熱點，必須記憶化。** 活躍密度、新出現的人、連續互動都會**逐筆紀錄**呼叫它，
  五萬多筆 × 十幾條 Regex —— 這是「切日期要跑很久」的主因之一。名稱其實只有幾百種，結果直接快取。
  用 `ConcurrentHashMap`：統計在背景執行緒跑，通知服務也會呼叫，兩邊會同時進來。
- **跟日期篩選無關的全表掃描要快取。** `fullScan()`（每個人的第一次／最後一次／活躍過哪些天）
  與 `getContributionMap()` 換日期完全不會變，卻各自掃過全表。
  快取用**引用比對**（`===`）當鍵：新紀錄進來時 `_interactions` 會換成新的 List 物件，
  引用自然對不上、快取自動失效，不需要維護任何 dirty flag。
  ⚠️ 活躍密度的快取鍵還要帶「今天」，跨日之後格子要往前推一格。

- ⚠️ **逐筆呼叫的函式裡絕對不能 `Calendar.getInstance()`。**
  它會做時區與地區設定查詢並配置物件。`startOfDay` 曾經這樣寫，
  而分析頁一次重算會經過 getStreaks / getContributionMap / extraStatsOf /
  getDailyTrend / getCoverage 好幾條全表掃描，每條對五萬多筆各呼叫一次 ——
  一次產生數十萬個 Calendar，這就是「分析要跑很久才出來」。
- 現行做法：Calendar 放 `ThreadLocal` 重複使用，再加一格「上一天」快取（紀錄依時間排序，
  相鄰筆數大多同一天，絕大部分呼叫會在第一個 if 就回傳）。
  `isWeekend`、`periodPredicate` 同理。

- ⚠️ **互動紀錄存在 `filesDir/RelateStats_Records.txt`，不是 SharedPreferences。**
  舊版每次存檔都把全部紀錄（實測 55,000+ 筆）轉 CSV、丟進 HashSet、再寫 XML，
  光序列化就要好幾秒；而通知一來就觸發一次，所以「每次通知跳出來 App 都會 LAG」。
- 是否需要重寫檔案用**參考比對**（`_interactions.value !== lastWrittenRecords`）判斷，
  **不要改用手動 dirty 旗標** —— 紀錄有十幾個地方會被改（新增、匯入、刪除、還原、
  清理、還原備份…），漏標任何一個就是資料沒存到。每次修改都會產生新的 List 實例，
  所以 `!==` 一定抓得到，而且是 O(1)。
- 存檔防抖 4 秒：訊息常常一串一串進來，合併成一次寫入。

- **絕對不要在 `remember {}` 裡做全表運算**。`remember` 是同步的，
  等於在主執行緒掃幾萬筆紀錄；而只要 key 包含 `records`，
  **每收到一則通知就重算一次**，訊息密集時畫面直接凍住 → ANR。
  正確寫法：`produceState` + `withContext(Dispatchers.Default)`，並在開頭加 `delay(300)` 合併連續更新。
- 全部四個頁面（總覽、洞察、排行、聯絡人）及詳情/逐筆紀錄對話框現在都走背景計算。
- 背景計算期間清單本來就是空的，**「沒有資料」的空狀態必須同時檢查 `ready`**，否則會閃一下。

### 常用詞相關

- **`wordSenders` 只記「誰傳過這個詞、幾次」，不記內容。** 那個前提不能破。
- ⚠️ 兩層上限是必要的：詞最多 400 個、每個詞最多 6 位發話者。
  不設上限的話這份資料會變成「詞數 × 聯絡人數」，比詞頻本身大一個量級。
- ⚠️ **這份資料只能從 v3.20 開始累積** —— 過去的訊息沒有留內容，發話者回推不出來。
  UI 上要明講，否則使用者會以為壞掉。

- ⚠️ **過濾規則跟清理規則是兩套，改一邊就要改另一邊。**
  `isSystemGeneratedText` 擋的是**整句**；但已經存進詞頻的是 **n-gram 碎片**
  （「標註您的訊息內容」被切成「標註」「註您」「您的」「訊息」「內容」……），
  清理走的是 `isJunkWord`。只補過濾規則、沒補 `JUNK_WORD_MARKERS` 與語料的話，
  **新資料乾淨、舊資料照樣髒**，使用者看到的完全沒變。
- 補強後要把 `runWordPurgeIfNeeded` 的旗標名稱換一版（目前 `word_purge_v30_done`），
  否則升級不會重跑。

- 過濾系統通知的 `SYSTEM_PHRASE` **絕對不能加 `^` `$` 錨點**。
  真實通知是「王小明傳送了一則貼圖」，前面掛著人名；
  加了錨點就變成整句要完全吻合才算數，結果一句都濾不掉，連人名都被當成常用詞。
- 命中系統句型時要**整句丟棄**，不能只切掉片語留下人名。
- v2.3 新增**回溯清理**：升級後自動跑一次，把舊詞頻裡的系統通知殘渣與
  **人名碎片**刪掉（保留其他累積，不會歸零）。需要再跑可到「設定 → 只清常用詞裡的系統通知與人名」。
- **人名沒有規則可以辨識**，只能拿聯絡人清單去比對。
  副作用：如果有聯絡人叫「美食」，「美食」這個詞也會被清掉。這是刻意的取捨。

### 通知（每晚回顧／服務被關）

- ⚠️ **通知只負責叫使用者點進來，不要把數字塞進通知內文。**
  不同手機的通知寬度不同，全形空白一換行就歪，也沒辦法跟昨天比。數字放在 App 內的 `RecapDialog`。
- 流程：通知 →（`EXTRA_OPEN_RECAP`）→ `pendingRecap = true` → 主畫面開概要彈窗 →
  關掉（✕／點外面／返回／「看完整報告」）一律切到分析頁、日期設成今天。
- ⚠️ **截圖模式只換「顯示」**：`RelateViewModel` 提供給畫面的 interactions／aliases／categories 等是假名版本，
  `DataRepository` 的真實資料不動。開啟期間所有以名字為參數的寫入都會被 `screenshotGuard()` 擋下 ——
  **新增這類寫入函式時，第一行一定要呼叫它**，否則會把假名字寫進真實資料。
  直接讀 `DataRepository` 顯示名字的地方（例如每日報告）要自己包 `ScreenshotMode.display()`。
- ⚠️ **群組判定不能只信 `android.isGroupConversation`**：LINE 群組常常不帶這個旗標。
  LINE 另外用「對話名 ≠ 發言人」與「名稱後有（人數）」判斷；這兩條**只能套在 LINE**，IG 一對一也會帶對話名。
  同一個名稱只要有一筆是群組，整個對話都算群組（`knownGroups`），使用者手動指定（`groupOverrides`）優先於一切。
- ⚠️ **滿版的 `Dialog`（`usePlatformDefaultWidth = false`）一定要 `safeDrawingPadding()`**，
  而且要搭配 `decorFitsSystemWindows = false` 才拿得到系統列邊界；另外再設高度上限，內容區自己捲動。
  否則底部按鈕會被系統導覽列／手勢條蓋住，使用者按不到。
- ⚠️ **手機原生電話的常駐通知一定要處理**（`appName == "電話"` 不能在常駐通知那段被排除）。
  撥號 App 接通後不會發一般通知，排除掉的話「我打出去的電話」永遠不會被記錄，
  使用者看到的就只有別人打給他的未接來電。接通的判斷＝通知上出現 `0:07` 這種計時或「通話中」，
  不能從「撥號中」就開始計時，否則響很久沒人接也會被記成一通。
- **通話方向靠「有沒有先跳來電通知」判斷**：對方打來會先鈴響再變成通話中，我方撥出只有通話中。
  ⚠️ 判斷不出來時 `callDirection` 留 0 顯示「通話」，不要猜 —— 寫錯方向比沒寫更糟。
- **意見回饋不可以自己送出**（App 沒有網路權限），只能開郵件草稿或複製到剪貼簿。
- ⚠️ **回顧彈窗的顏色一律取自目前配色**（`pal.brand`／`accent`／`colors`／`tagStyle`），不要寫死色值 ——
  選了奶茶色盤卻跑出藍色標頭，整個彈窗就跟 App 其他地方脫節。
- 回顧彈窗用自己的 `Dialog`（`usePlatformDefaultWidth = false`）而不是 `AlertDialog`，標頭漸層才能滿版到圓角邊。
  內容區可捲動、按鈕固定在底部，字體放大時不會把「看完整報告」擠出畫面。
- ⚠️ **`MainActivity.onNewIntent` 一定要處理旗標。** App 已經開著時點通知不會走 `onCreate`，
  少了 `onNewIntent` 就只是把 App 叫到前景，彈窗不會出現。

- 用 `AlarmManager.setWindow`，不是 WorkManager、也不是精確鬧鐘：
  「晚上九點左右」不需要分秒不差，而精確鬧鐘在 Android 12+ 要另外的權限。
- ⚠️ **`setWindow` 是一次性的，觸發後要自己排下一次**（`RecapReceiver` 結尾）。
- ⚠️ **每次 App 啟動都要重排一次。** 鬧鐘會被「強制停止」清掉，只靠 `BOOT_COMPLETED` 補不回來。
  重複排同一個 `PendingIntent` 不會累加。
- 今天沒有真人互動就**不發**回顧 —— 沒事不要吵人。
- 無障礙服務被關時發高優先度提醒；服務正常時主動 `cancel` 掉那則通知。

### 通話統計相關

- **LINE、Messenger 等 App 的通話時長 = 「通話中」常駐通知 post 到 remove 的時間差。**
  不讀內容、不需要額外權限。`ongoingCalls` 用 `putIfAbsent` —— 通話中通知每秒都會重新 post。
  3 秒以下（沒接通）與 6 小時以上（通知卡住）不記。
  ⚠️ 同一通電話如果 App 事後又發「通話結束 3:21」，`recentEndedCalls` 會擋掉 2 分鐘內的重複計算。
  ⚠️ 未實機驗證：少數 App 或機型不會掛「通話中」通知，或標題不是對方名字。

- **Android 原生撥號 App 接通後不發通知**，所以只靠通知監聽永遠拿不到接通通話的秒數。
- ⚠️ **不要再加回「匯入手機通話紀錄」**（v3.28 移除）。`READ_CALL_LOG` 是 Play 受限權限，
  只有預設電話／簡訊 App 等少數用途能用，加回去就過不了審。舊資料裡 `calllog-` 開頭的紀錄保留不動。
- 台灣原生撥號 App 的字樣是「**未接電話**」不是「未接來電」，兩者都要比對。
- 平均時長只能除以「真的抓到秒數的通數」，不能除以接通數，否則會被稀釋成 0。

### 兩頁的分工

- **概況（原總覽）＝ 這段期間有多少、誰佔多少**（量與構成）
- **分析（原洞察）＝ 時間上的規律、跟過去比、關係的變化**（模式與變化）

判斷新卡片要放哪一頁，就問它回答的是哪一種問題：
「誰／什麼佔多少」→ 總覽；「什麼時候／跟以前比／關係怎麼了」→ 洞察。

### 時間範圍的規則

**凡是會讓人問「這是哪段時間？」的數字，一律跟隨日期篩選。**
做不到或刻意不跟隨的，必須在卡片標題旁用 `ScopeTag` 標明：

| 指標 | 範圍 | 原因 |
|---|---|---|
| 常用詞 | 全期間 | 只存詞頻不存原文，事後無法重新切詞，技術上不可能分期 |
| 活躍密度 | 近數月 | 它的用途就是長期視圖，跟隨篩選會只剩一格 |
| 連續互動天數 | 全期間 | 連續天數本質是長期指標 |
| 聯絡人詳情的近 8 週趨勢 | 固定 8 週 | 同上，用來看長期關係變化 |
| 關係變化 | **跟隨** | 但判斷「新不新」必須回頭看完整歷史，卡片內已用 ⓘ 說明 |
| 跨平台聯絡 | **跟隨**（v2.9 修正） | 「本期有幾個人從多個平台找你」是期間問題 |
| 社交人格 | 跟隨 | 換範圍就可能換人格，卡片內已說明它描述的是「這段期間的你」 |

### 洞察區塊順序

- 洞察頁的區塊不是直接 `item{}` 出去，而是先收集成 `List<Sec>`，
  再依使用者存的順序輸出。收集與輸出在同一個 `content` lambda 裡，收集在前輸出在後。
- 容器宣告在 lambda **內部**，每次重組都是新的，不會累加。
- **新增區塊時要同時加進 `INSIGHT_SECTIONS` 常數**，否則排序對話框看不到它
  （不加也不會壞，只是排不到，會被接在最後面）。
- 排序對話框吃的是常數清單而不是「這次畫了哪些」：有些區塊沒資料時不會畫出來
  （例如通話統計），但使用者還是應該能先幫它排好位置。
- ⚠️ 不要在 `LazyColumn` 的 content lambda 裡寫 Compose state
  （一度用它記錄「畫了哪些區塊」），會造成重組迴圈。

### 刪除與封鎖

- **清除資料的文案要照實寫「會刪什麼、不會刪什麼」。** 舊版寫「淨化」「徹底重置所有標籤與連線資料」，
  聽起來像會清掉標籤與合併，使用者根本不敢點 —— 實際上只刪互動紀錄、會先預覽、會進最近刪除。

- **每個破壞性動作都要有「什麼都不做」的出口。** 非真人來源的提醒卡只給「標為系統通知」與「刪除」時，
  使用者若兩個都不想選，橫幅就每次開 App 都跳 —— 等於被逼著在兩個不想要的選項裡挑一個。
  第三個出口是 `junkIgnored`（記住它是真人，不再列入提醒），
  ⚠️ 而且**必須可以反悔**：設定頁的「已保留的來源」可以逐個取消保留。
- **批次清理一律可以逐項取消勾選，不做一鍵全清。** 判定靠規則就一定有誤判，
  而清掉的累積次數回不來。`WordPurgeDialog` 與 `JunkReviewDialog` 都是預設全勾、可搜尋、可個別取消。
- **刪除聯絡人時就要能勾「同時加入永不記錄名單」。** 光刪除擋不住對方再傳訊息，
  紀錄會被重新建立，使用者以為沒刪掉。預設不勾 —— 多數刪除是整理資料，不是要封鎖一個人。

- **所有破壞性動作一律二次確認，而且要寫明「刪的是什麼」**，不能只丟一句「已清掉 N 個」。
  `ConfirmDialog` 的 `details` 參數就是為此存在的：把即將消失的項目列出來。
  已套用於：整理系統通知、清掉常用詞雜訊（`previewJunkWords()`）、清除常用詞、清理異常紀錄、
  垃圾桶的永久刪除、聯絡人頁的「刪除並封鎖」。
  ⚠️ 預覽清單一定要 `remember` 住 —— `peekTrash()` / `previewJunkWords()` 會讀檔或掃全表，
  直接寫在參數裡等於每次重組都跑一遍。

- 刪掉聯絡人後對方再傳訊息，紀錄會被重建、人又冒出來。
  App 會在聯絡人頁頂部問你要「保留」還是「刪除並封鎖」。
- **封鎖是在通知服務最源頭擋掉**，不會再產生任何紀錄。
- 封鎖是單向門，所以一定要從「設定 → 永不記錄名單」看得到並能解除。

### 圖示相關

- App 圖示是**向量**（`drawable/ic_launcher_foreground.xml` + `ic_launcher_background.xml`），
  沒有點陣素材，改色改形狀直接編輯 XML 即可。
- 前景所有圖形必須落在 108 畫布的**中央 72x72 安全區（18..90）**內，
  否則各家廠商的圓形／方形／squircle 遮罩會把邊緣切掉。
- `mipmap-anydpi-v26/` 是 adaptive-icon；`mipmap-anydpi/` 是 API 24-25 的 layer-list 後備，
  後備用負 inset 把前景放大回來（舊系統不套遮罩，不放大會顯得很小）。
- 標題列的 logo 是 Compose Canvas 畫的同一個記號，改圖示時記得一起改。
- **不要用細線或細環**。圖示縮到 16px 時，108 畫布上小於約 10 單位的形狀
  不到 1.5px，線會整條消失。「關係」這種概念只能用**實心形狀的交疊**來表達，
  不能用連線。

### 出錯時怎麼查

- 四個統計頁的 `build*` 都包在 `runCatching` 裡。算到一半丟例外**不會讓 App 閃退**，
  會保留上一份資料並把堆疊寫進 `RelateStats_LastCrash.txt`。
- 有紀錄時，**設定頁最上方**會出現紅色區塊，一鍵複製完整堆疊。
  （以前只埋在診斷對話框裡，使用者根本不會去看。）
- `installCrashReporter` 仍然攔真正的未捕捉例外，兩者寫同一個檔。

### 資料安全

- 刪除紀錄（清除區間、刪除聯絡人）都會先進**紀錄垃圾桶**，保留 **7 天**，
  可在「設定 → 最近刪除」個別還原或立刻永久刪除；超過 7 天啟動時自動清掉。
- 還原用紀錄 id 去重，重複按不會變成兩份。
- 這跟「復原上一步」是兩套：復原只有一份最新快照，垃圾桶是每次刪除各留一批。
- 清除資料前會列出範圍內每位對象與筆數，**預設全勾＝全刪，取消勾選就保留**。

### 標籤相關

- **「自訂暱稱」必須是看得出來的按鈕**（實心膠囊＋✎），不能只是一行藍字 —— 跟名字排在同一列時根本看不出能按。
- ⚠️ **改任何功能、按鈕文字都要同步更新 `USER_GUIDE` / `USER_FAQ`**，說明寫的按鈕名稱必須跟畫面上一字不差。
- ⚠️ **帳號名稱一律可以長按（或點）展開全名。** 群組帳號開頭常常一樣（「(lavender_0806) …」），
  單行截斷後八個帳號看起來完全相同，根本分不出要拆哪一個。
- **合併的帳號必須能看得到、能拆、能選名稱**，全部在 `ContactAccountsDialog`（帳號與名稱）。
  入口：點聯絡人 → 選單第一項；卡片上「已合併 N 個帳號 ›」；合併完成後自動打開。
  `unmergeAccount()` 只刪別名、不動紀錄，綁錯了可以無損拆回來。
  ⚠️ 剛合併完 `cb.rawByUnified` 還沒被背景重算，對話框要自己補上 `aliases.filterValues { it == t }`，
  否則看不到剛綁進來的那個帳號。
- 聯絡人頁的標籤篩選是一排膠囊，**每顆直接寫人數**。「全部」不含系統通知，與清單預設顯示規則一致。

- **「未分類」與「系統通知」可以改名換色，但不能刪除**。前者是分類的 fallback，
  後者用於排行降噪，程式內部有依賴，刪除鍵會是灰色的。
- 刪除其他標籤時，原本屬於它的聯絡人會退回「未分類」，互動紀錄不受影響。
- **兩頁的手勢定義：長按 = 進多選，點一下 = 開這個人的操作選單。**
  聯絡人頁以前反過來（長按開選單、點一下沒反應），結果捲到一半想批次分類時，
  唯一的入口（上方「選取」鈕）早就滑掉了。
- **排行頁與聯絡人頁的批次分類手勢要一致**：長按任一列進多選並勾起該列，
  底部浮出 `BatchTagBar` 選標籤。上方的「選取」按鈕是備援入口，不是唯一入口。
  ⚠️ 長按必須寫在 `RankRow` **內層那一列**上。那一列自己就吃掉點擊事件了，
  在外面包 `combinedClickable` 收不到手勢。

### 垃圾聯絡人判定

- `listJunkContacts()` 的定義是「**是非真人** 而且 **還沒被標成系統通知**」，
  跟 `previewRetagTargets()` 一致。不要寫成 `or`，也不要把已標記的算進來 ——
  那樣標記完數字一個都不會少，橫幅永遠關不掉。
- ⚠️ **聯絡人頁的 `produceState` key 必須含 `categoriesMap`。**
  垃圾來源清單、分類篩選都吃標籤，少了它，標籤改完畫面不會更新。
- 聯絡人頁與排行頁一樣，**預設不顯示「系統通知」**；把標籤篩選切到它才看得到。
- **橫幅「N 個非真人來源」點得進去**（`JunkReviewDialog`），一列一列看名稱、平台、筆數、
  最近時間與**命中的規則**，可取消勾選誤判的再整批標記。理由字串由 `junkReason()` 產生，
  ⚠️ 它的判斷順序必須跟 `isNonPersonContact()` 一模一樣，否則顯示的理由會對不上實際命中的規則。
- ⚠️ **這一頁能顯示的「是哪則通知」就是通知標題本身**（也就是聯絡人名稱）、平台、筆數與時間。
  本 App 不保存訊息原文，不要為了做得更詳細去存內容 —— 那會直接破壞「不讀取訊息內容」這個前提。

- 用規則比對辨識非真人通知（`1000+ 個新的讚`、`11 位新追蹤者`、`XXX 的串文`、促銷推播等）。
- 這些名稱把數字寫進名稱裡，所以同一種通知會被拆成數十個獨立「聯絡人」，是清單爆量的主因。
- **規則有可能誤判**（例如群組真的叫「推薦好物」）。因此預設是**歸類到「系統通知」而非直接刪除**，
  誤判時可自行改標籤救回來。要永久刪除請按聯絡人頁的「一鍵清除」，該操作**無法復原**。

### 備份相關

- **Android 自動備份有 25MB 系統上限**。資料量大時請改用「備份到雲端」手動備份。
- **完整的 Google 帳號登入 + Drive API 同步尚未實作**。需要先到 Google Cloud Console
  建立專案、申請 OAuth Client ID 並註冊 App 簽章 SHA-1 —— 這部分只有專案擁有者能做。
  目前以 Android 自動備份與 Share Intent 替代。
- 備份檔可達十幾 MB，因此是透過 FileProvider 傳檔，不是塞進 Intent 的 EXTRA_TEXT
  （那樣會超過 Binder 傳輸上限直接閃退）。

### 開發相關

- 主要邏輯目前全在單一檔案 `app/src/main/java/com/example/relatestats/MainActivity.kt`（約 3,600 行）。
- `getDeviceUsageTimeSec()` 裡有一段警告註解務必保留：Kotlin 的 `/` 優先序高於 `?:`，
  寫成 `a ?: 0L / 1000L` 會讓 `/1000` 只套用在預設值上，導致回傳毫秒卻被當成秒。
  這個 bug 曾讓畫面顯示 742,246 小時。
- 無障礙服務設定 `accessibility_service_config.xml` 的 `flagReportViewIds` **不可移除**，
  少了它 `findAccessibilityNodeInfosByViewId()` 永遠回傳空，會導致抓不到聊天室名稱。
- **聊天室標題不可用寫死的完整 view id 比對**。IG / Threads 幾乎每次改版都會換 id 前綴，
  寫死等於下次改版就失效（v1.6 前 Threads 完全偵測不到時長就是這個原因）。
  現在是「view id 後綴比對 + 畫面頂端文字」兩層策略。
- **停留時間偵測需要容錯**。單次抓不到標題多半只是畫面重繪，立刻結算會把連續停留
  切成大量不足 1 秒的碎片而被丟棄。現在是連續 3 次抓不到才算離開，且 25 秒內回到
  同一聊天室會接續累加。
- **節點樹一定要用 BFS 走訪**。標題列在淺層、訊息列表又深又寬，用 DFS 會先鑽進訊息
  列表，節點預算在碰到標題前就耗盡（v1.6→v1.8 之間只有 LINE 抓得到就是這個原因）。
- **不可硬性要求偵測到輸入框**才認定在聊天室。IG / Threads 的輸入框常包在摺疊容器裡，
  或未取得焦點時不回報 `isEditable`。標題若來自已知 view id 就足以採信。
- **`snapshotForUndo()` 的狀態必須同步擷取**，不能整段丟進背景協程 ——
  呼叫端會在回傳後立刻改資料，否則快照會拍到已刪除後的狀態。
- `Notification.MessagingStyle` 規格：**`sender` 為 null 代表訊息由使用者本人發出**，
  必須排除，否則自己發的訊息會被算成收到的。
- **群組判定「只」能信 `android.isGroupConversation`**。不可用 `conversationTitle`
  是否存在來推斷（IG 連一對一私訊都會帶），**也不可用「多位不同發言人」**——
  Instagram 會把多個不同的一對一私訊打包進同一則通知，發言人自然不只一位，
  誤判會把不同的人全部併成同一個群組（v2.1 修）。
- **`produceState` 的 key 不可直接放會頻繁變動的大型集合**。通知服務持續寫入時
  `_interactions` 每次都是新實例，會讓整包統計不斷取消重啟直到 ANR。
  producer 開頭要 `delay(300)` 讓連續變動合併成一次計算。
- 修改後請務必跑一次 `assembleDebug` 確認可建置，再 commit。
- **UI 一律使用 `T`（字級）與 `D`（間距）代幣**，不要再寫死 sp / dp 數值，否則密度會再度失控。
- **長列表必須用 `items` / `itemsIndexed` 逐列渲染**，不可塞進單一 `item` 的 Column ——
  聯絡人有 700+ 位，那樣會一次組完所有節點直接卡死。
- **統計計算一律不可在 composition 期間同步執行**。資料量是 9 萬筆等級，
  一次全表掃描就有感，十次就是 ANR。統一走 `buildOverview()` / `buildInsights()`
  一次算完，再用 `produceState` + `Dispatchers.Default` 丟背景（v2.0 的當機主因）。
- **任何寬度不可控的文字都要加 `overflow = TextOverflow.Ellipsis`**（聯絡人名稱、時長字串），
  只設 `softWrap = false` 會變成硬裁切。
- **絕對不要用 `Surface(color = …, modifier = Modifier.clickable { … })` 做按鈕**。
  Material3 非可點擊的 `Surface` overload 內部有 `.pointerInput(Unit) {}`，會在事件抵達
  外層 `clickable` 前就消耗掉，按鈕完全沒反應（v1.9 一次修掉五顆這樣寫的按鈕）。
  要嘛用 `Surface(onClick = …)` overload，要嘛用 `Box` + `clip`/`background`/`clickable`。
- **同一列的卡片要固定高度**。有副標與沒副標的卡片高度不同，並排就是跑版。
- **`versionName` 現在會直接顯示在 App 設定頁最下方**（`BuildConfig.VERSION_NAME`）。改版號只需要改 `app/build.gradle.kts` 一處，App 內畫面與 CHANGELOG 版本號要盡量保持一致。
