# 修復紀錄

## v1.1（2026-08-26）— 系統性除錯

針對「訊息統計不進去 / 閃退卡頓 / 跑版 / 統計數據不實」做的全面盤查與修復。
以下依照使用者感受到的症狀分類，每一項都標示根因。

---

### A. 訊息統計不進去

| # | 根因 | 修法 |
|---|------|------|
| A1 | 通知服務算出 `isCall` / `isMissedCall` / `subSender` / `finalWordCount`，**卻沒有放進 `InteractionRecord`**。 | 全部正確帶入紀錄。 |
| A2 | `InteractionRecord.toCsvString()` 只序列化 8 個欄位，`isMissedCall` / `isCall` / `subSender` **存檔即遺失**。重開 App 後通話數、未接來電、群組發言排行永遠是 0。 | 擴充為 11 欄位（V12），並保留讀取舊 8 欄位資料的相容性。 |
| A3 | 雜訊過濾用 `content.contains("正在")`、`contains("上傳")`、`contains("影片")` 等寬鬆比對，「我正在路上」「影片我看過了」這類**真實訊息被整句丟掉**。 | 改為「整則內容等於雜訊」或「以雜訊前綴開頭」才略過。 |
| A4 | 一次收到多則訊息時系統只 post 一則通知，舊版只記 1 則。 | 解析 `android.messages`（Notification.EXTRA_MESSAGES），逐則計入並記錄處理進度避免重複。 |
| A5 | 群組判斷讀 `android.isGroup`，但正確的 key 是 `android.isGroupConversation`，該判斷**永遠是 false**。 | 兩個 key 都讀。 |
| A6 | 服務先於 Activity 啟動時（例如開機後）`prefs` 尚未建立，`saveData()` 靜靜地什麼都沒寫。 | `addInteraction` 明確擋掉未初始化狀態，並在 `onListenerConnected()` 補呼叫 `init()`。 |
| A7 | 通知服務任何一次例外都會被系統停用，之後全部收不到。 | 整個處理流程包在 try/catch 內。 |

### B. 停留時間統計不實（畫面出現 742246 小時）

| # | 根因 | 修法 |
|---|------|------|
| B1 | `getDeviceUsageTimeSec()` 寫成 `stats?.sumOf{...} ?: 0L / 1000L`。Kotlin 中 `/` 優先序高於 `?:`，**`/1000` 只套用在預設值 `0L` 上**，真正的加總完全沒除以 1000 → 回傳毫秒卻當秒用。 | 先取值再除，並改用 `queryAndAggregateUsageStats`，回傳型別改 Long。 |
| B2 | 無障礙服務遇到非目標 App 直接 `return`，**碼錶永遠不會停**。切去別的 App、回桌面、關螢幕，時間都繼續累加到最後一個聊天室頭上。 | 非目標 App 一律先 `leaveChat()` 結算。 |
| B3 | 沒有處理關螢幕。整夜掛在聊天室 → 隔天一開就是好幾小時。 | 註冊 `ACTION_SCREEN_OFF` / `ACTION_USER_PRESENT` 廣播強制結算，並在 `onUnbind` / `onDestroy` / `onInterrupt` 一併結算。 |
| B4 | 單次上限寫成 3600 秒（藍圖規定 1800），且超過上限時**記成上限值**，一樣虛胖。 | 上限改回 1800 秒，超過視為背景掛機直接丟棄。 |
| B5 | 所有加總用 `Int`，資料量一大就整數溢位變負數或天文數字。 | `SenderStat` / `AppUsageStat` / `CategoryStat` / `HourlyStat` 的時長欄位全面改 `Long`。 |

### C. 抓不到聊天室名稱、出現假聯絡人

| # | 根因 | 修法 |
|---|------|------|
| C1 | `accessibility_service_config.xml` 的 `accessibilityFlags` 只有 `flagDefault`，**缺少 `flagReportViewIds`**。依 Android 規格，沒有這個 flag 時 `findAccessibilityNodeInfosByViewId()` 不會回傳任何節點 → `extractChatName()` 永遠是 null。 | 補上 `flagReportViewIds｜flagIncludeNotImportantViews｜flagRetrieveInteractiveWindows`。 |
| C2 | 因為 C1 抓不到標題，舊碼退而用 `event.text.firstOrNull()`——那通常就是**訊息內容本身**，於是訊息文字被當成聯絡人名稱，建出一堆假聯絡人並瓜分停留時間。 | 移除該退路，只信任明確的標題 view id。 |
| C3 | `accessibilityEventTypes` 只宣告 `typeWindowStateChanged`，但程式碼在判斷 `TYPE_WINDOW_CONTENT_CHANGED`——該事件根本收不到。 | 兩種事件都宣告，並在程式端節流。 |
| C4 | 聊天室名稱 `length < 25` 的限制會把長群組名整個濾掉。 | 放寬到 60 字。 |

### D. 卡頓 / ANR

| # | 根因 | 修法 |
|---|------|------|
| D1 | 每收到一則通知就把**整份紀錄重新序列化並寫檔**，而且是同步執行。 | 改為背景執行緒 + 1.5 秒去抖動合併寫入；使用者操作（合併、標籤、清除、匯入）則立即寫入。 |
| D2 | `TYPE_WINDOW_CONTENT_CHANGED` 滑動時每秒觸發數十次，每次都**走訪整棵節點樹**。 | 1.2 秒節流，並限制遞迴深度 12 層／節點數 400。 |
| D3 | 聯絡人分頁對每位聯絡人都掃一次完整紀錄（O(聯絡人×紀錄)），且沒有 `remember`，每次重組重算。 | 改用 `groupingBy().eachCount()` 一次算完並加上 `remember`。 |
| D4 | 「標籤互動分析」與聯絡人詳情的 24 小時統計都沒有 `remember`，對話框開著就持續重算。 | 全部加上 `remember`。 |
| D5 | 匯出／匯入在主執行緒讀寫檔案。 | 移到 `Dispatchers.IO`。 |
| D6 | 紀錄數無上限成長，存檔越來越慢。 | 上限 200,000 筆，超過保留最新的。 |

### E. 閃退

| # | 根因 | 修法 |
|---|------|------|
| E1 | `loadData()` 中 `catSet.associate { it.split("|=|").let { it[0] to it[1] } }`，任何一筆資料格式壞掉就拋 `IndexOutOfBoundsException`——**一開 App 就閃退**。 | 每段獨立防護，壞掉的那筆丟棄，其餘照常載入。 |
| E2 | 名稱中若含 `|#|`、`|=|`、`;`、`\|\|` 會讓 CSV 解析錯位，整批紀錄讀不回來。 | 存檔前消毒分隔符號。 |
| E3 | `importBackupString` 沒檢查欄位數，備份檔略有損毀就 `parts[4]` 越界。 | 檢查 `parts.size` 並驗證解析結果。 |
| E4 | `getStartOfWeekTimestamp` 的 `while` 迴圈在 `startDay` 值異常時**無限迴圈直接 ANR**。 | 加上合法值檢查與最多 7 次的迴圈上限。 |
| E5 | 進度條 `currentScore / maxScore` 在 maxScore 為 0 時產生 NaN。 | 防護並 `coerceIn(0f, 1f)`。 |

### F. 跑版

| # | 根因 | 修法 |
|---|------|------|
| F1 | App 用量列的數值 `Modifier.width(60.dp)` 固定寬度又沒鎖單行，`"250888h 41m"` 這種長字串被折成三行（截圖中的破版）。 | 改 `widthIn(min=60.dp)` + `maxLines=1, softWrap=false`。 |
| F2 | 時段百分比同樣的固定 `width(40.dp)` 問題。 | 同上。 |
| F3 | 「平台數位健康」的大數字在 Row 中沒有溢位保護，數字一大整排擠爆。 | 改為單行 + 橫向捲動。 |
| F4 | `ContactDetailDialog` 內容在小螢幕會被裁掉。 | 加上垂直捲動與最大高度。 |
| F5 | 「清除特定日期」的日曆被固定 `height(300.dp)` 切掉。 | 改 `heightIn(max=420.dp)` + 可捲動。 |
| F6 | `MinimalCalendar` 固定以「週日」開頭，和設定頁的「一週起始日」不一致，日期整排錯位。 | 依設定值旋轉星期標題與起始位移。 |
| F7 | 內容區沒有導覽列避讓。 | 補 `navigationBarsPadding()`。 |

### G. 統計邏輯不一致

| # | 根因 | 修法 |
|---|------|------|
| G1 | `getLeaderboard` 與 `getDynamicLeaderboard` **各寫一份規則且互相衝突**（一個把未接來電算進訊息、另一個不算），總覽點進去的排行與排行分頁對不起來。 | 合併為單一 `buildStats()`。 |
| G2 | `SenderStat.incomingCount` 實際存的是「全部紀錄筆數」，「依互動頻率」排序其實在排停留紀錄筆數。 | 拆成 `recordCount`（全部）與 `incomingCount`（真正收到的），排序改用 `msgCount + callCount`。 |
| G3 | 排行榜長條圖的基準與排序基準不一致，第一名的長條不一定最長。 | 統一基準。 |
| G4 | 帳號合併只跳一層：「A 併到 B，再把 B 併到 C」之後 A 仍停留在 B，同一人被拆成兩筆。 | 目標解析到最終節點，並把原本指向 A 的別名一起改指；加上循環偵測。 |
| G5 | 聯絡人清單是 `aliases.values + 所有原始名稱`，**被合併掉的舊名稱仍留在清單上**，同一人合併後反而變成兩張卡片。 | 一律先歸戶再去重。 |
| G6 | 通話時長正則只認得「12分34秒」，其他格式（`1:02:03`、`1小時2分`）一律算 0。 | 支援多種格式。 |
| G7 | IG 群組訊息的字數把「發言人 :」前綴也算進去。 | 先剝除前綴再計字數。 |
| G8 | 同一則訊息被重複 post（已讀、摘要）就重複計次，訊息數虛胖。 | 依 `key + when + 內容` 去重，並排除 `FLAG_GROUP_SUMMARY` 與常駐通知。 |
| G9 | 撥號 App 的「通話中」常駐通知會被當成一則訊息記進去。 | 撥號 App 只產生通話紀錄。 |
| G10 | 「全部」時間範圍下手機總用量直接回 0，佔比分析永遠不出現。 | 以最早一筆紀錄為起點查詢。 |

## v1.2（2026-08-26）— 舊資料清理與資料管理功能

v1.1 修好了「產生錯誤資料」的程式碼，但**手機裡已經累積的 11.9 萬筆舊資料不會自己變乾淨**，
所以畫面上仍然顯示 88 萬小時。這一版處理殘留資料，並補上使用者找不到的功能。

### 實機資料驗證（Samsung R5CY74AA3SY，2026-08-26）

從裝置撈出 `RelateStatsData.xml`（17.9 MB）分析：

| 紀錄類型 | 筆數 |
|---|---|
| 訊息紀錄（durationSeconds = 0） | 88,890 |
| 停留時長 ≥ 100 萬秒（不可能值） | 30,453 |
| 停留時長 3,601〜100 萬秒 | 35 |
| 停留時長 1〜3,600 秒（正常） | 5 |

單筆最大值達 999,000,000 秒（約 31 年）。所有異常值都是 1000 的倍數，
代表舊版把毫秒直接當成秒存入，再加上碼錶不會停，累積成天文數字。

**同時確認 v1.1 的修復有效**：新版安裝後產生的 3 筆紀錄，時長分別是 0 秒與 4 秒。

### 修正

- **自動清理異常紀錄**：升級後首次啟動時，自動移除 `durationSeconds` 超過 30 分鐘上限
  或時間戳無效的紀錄。清理前會先把完整原始資料另存到 App 內部空間
  （`RelateStats_PreCleanup_<timestamp>.txt`）。
  實測：119,383 → 88,893 筆，總時長 742,246,961 小時 → 0.8 小時，
  本日 880,269 小時 → 0.8 小時，**訊息紀錄零損失**。
- **資料管理改成看得見的功能**：舊版入口是設定頁最底下 12sp、50% 透明度的灰色小字，
  幾乎不可能被發現。改為正式區塊，直接顯示目前紀錄筆數、異常筆數，
  並提供「清理異常紀錄」與「清除資料（今日／本週／指定日期／全部）」兩個按鈕。
- **新增「備份到 Google 雲端硬碟 / LINE Keep」**：藍圖 §8.1 規劃但從未實作。
  走系統分享選單（`Intent.createChooser`），不需登入 Google 帳號或串接任何 API。
- **新增 FileProvider**（`res/xml/file_paths.xml` + manifest 宣告）：
  備份檔透過 FileProvider 傳遞而非塞進 `EXTRA_TEXT` —— 備份字串可達十幾 MB，
  放進 Intent 會超過 Binder 傳輸上限直接閃退。這同時也是日後整合分享卡片的前置作業。
- 單次停留上限抽成共用常數 `MAX_STAY_SECONDS`，服務端與清理判定共用同一個值。

### 說明

歷史的「停留時間」資料無法還原——原始值就是錯的，除以 1000 之後仍然是
「連續掛在同一個聊天室好幾天」的無意義數字。停留時間會從安裝新版後重新開始正確累積。
訊息數、字數、聯絡人與標籤則完整保留。

## v1.3（2026-08-27）— 通知降噪、合併強化、新統計與介面瘦身

### 通知降噪

- 新增內建標籤「系統通知」。`isNonPersonContact()` 以規則比對辨識非真人通知
  （「1000+ 個新的讚」「11 位新追蹤者」「XXX 的串文」「限時優惠」等），
  自動歸到此標籤，**排行榜預設不顯示**，指定該標籤時才列出。
- 採「歸類」而非「刪除」：規則有誤判時使用者仍可自行改標籤，不會遺失資料。
- 設定頁提供「整理系統通知」按鈕，可隨時對既有聯絡人重跑一次歸類。

### 聯絡人合併

- 合併對象改為**可搜尋的對話框**，取代原本要滑很久的下拉選單。
- 新增**自動合併相似帳號**：忽略 emoji、空白、標點與大小寫後比對，
  再加上「一方包含另一方」的判斷，把建議群組列出讓使用者勾選確認，
  預設併入互動量最高的那個名稱。

### 排行

- 新增「全部／個人／群組」分段篩選，直接在排行頁切換。
- 移除「詳細排行數據」標題列，改由篩選器與排序鍵共用同一行。

### 新統計

- **活躍熱力圖**：星期 × 小時的 7×24 網格，顯示互動集中在哪些時段。
- **常用詞**：中文取雙字組、英數取單字，內建停用詞表，取前 12 名。
  只累計詞頻、**不保留訊息原文**，上限 3000 個詞。
  註：歷史訊息只存了字數沒存內容，無法回推，從本版開始累積。

### 介面密度

列表內距 20/24 → 14dp、區塊間距 20 → 12dp、卡片內距 20 → 14dp、
卡片圓角 20 → 14dp、大數字 36 → 28sp、人格卡標題 22 → 18sp、
排行卡名稱與時長 18 → 16sp、標籤卡寬度 130 → 112dp。

### 備份

- 補上 Android 自動備份設定：`backup_rules.xml` 與 `data_extraction_rules.xml`
  原本都還是空白範本，等於從未真正設定。現已明確指定備份 `RelateStatsData.xml`，
  資料綁定手機登入的 Google 帳號，換機重裝後自動還原。
- 設定頁加上說明卡，並註明系統上限 25MB。

### 其他

- 程式碼註解全面精簡：移除逐條說明「舊版怎麼錯」的長段落，
  保留「為什麼要這樣寫」的關鍵提示（例如 `?:` 優先序陷阱）。
  完整的問題根因保留在本文件，不佔用程式碼空間。

### 已知限制

- **完整的 Google 帳號登入 + Drive API 同步尚未實作**。需要先在 Google Cloud Console
  建立專案、申請 OAuth Client ID 並註冊 App 簽章 SHA-1，這部分需要專案擁有者操作。
  目前以 Android 自動備份（綁定帳號、自動還原）與 Share Intent 備份替代。
- 常用詞統計為全期間累計，不隨日期篩選變動。

## v1.4（2026-08-27）— 垃圾聯絡人一鍵清除、多選批次分組

### 一鍵清除垃圾聯絡人

聯絡人頁最上方會顯示紅色提示卡「N 個垃圾聯絡人」，按「一鍵清除」即可全部刪除
（含互動紀錄、標籤與合併設定），刪除前會列出名單確認。

實測使用者資料：846 位聯絡人中有 **144 位是垃圾**，刪除後剩 702 位真人聯絡人。
這些垃圾名稱把數字寫進名稱裡（`1 個新的讚`、`10 個新的讚`、`100+ 個新的讚`、
`11 位新追蹤者`…），所以同一種通知會被拆成數十個獨立「聯絡人」，
這正是聯絡人清單爆量的主因。

### 多選批次分組

- 標題列新增「選取」按鈕進入多選模式。
- 多選模式下每張卡片顯示勾選框，點卡片任一處即可切換選取。
- 底部固定操作列：顯示已選人數、全選／取消全選、**設定標籤**（一次套用到所有選取者）、**刪除**。
- 批次設定標籤只寫一次檔（`updateCategories()`），不會每改一位就存一次。
- 多選模式下卡片自動收合「綁定其他帳號」列並縮小標籤為唯讀徽章，一屏能看到更多人。

### 相關新增

- `DataRepository.deleteContacts(names)`：刪除指定聯絡人的紀錄、別名與標籤。
- `DataRepository.updateCategories(names, categoryId)`：批次設定標籤。
- `DataRepository.listJunkContacts()`：列出非真人或已歸類為系統通知的聯絡人。

## v1.5（2026-08-27）— 標籤完全可自訂

### 預設標籤

改為 **家人／另一半／朋友／工作／未分類／系統通知**（新增「另一半」，並依常用度排序）。
這些只是「首次啟動的種子清單」，名稱與顏色之後都可以改。

### 標籤管理

新增「標籤管理」對話框，兩個入口：
- 設定頁 →「標籤管理」（右側顯示前四個標籤的色點預覽）
- 聯絡人頁 →「全標籤」下拉 →「⚙ 管理標籤」

可做的操作：
- **改名**：包含內建的家人／朋友／工作，全部都能改成自己習慣的字樣
- **換色**：18 組預選配色（6 組內建色 + 12 組自訂色盤），點方塊即選
- **排序**：上下箭頭調整順序，會反映到所有標籤選單與篩選器
- **刪除**：成員自動退回「未分類」，互動紀錄不受影響
- **新增**：可自行指定名稱與顏色（舊版是隨機配色）

「未分類」與「系統通知」的 id 程式內部會用到（前者是分類 fallback，
後者用於排行降噪），因此**可以改名換色但不可刪除**，刪除鍵會呈現灰色。

### 底層變更

- 標籤清單改為**整份持久化**（`all_categories`，含順序），不再是「寫死的內建 + 自訂」兩段式。
  內建標籤因此才能改名換色。
- 升級時自動從舊的 `custom_categories` 遷移：種子清單 + 既有自訂標籤，
  現有聯絡人的分類設定完全不受影響。
- 匯出／匯入改為包含完整標籤清單；讀到舊備份（只有自訂標籤、缺 `OTHER`）時
  會自動補回種子清單。
- 新增 `updateCategoryMeta()` / `deleteCategory()` / `moveCategory()`；
  `ensureEssential()` 保證 OTHER 與 SYSTEM 一定存在。

## v1.6（2026-08-27）— 時長偵測重寫、IG 歸戶修正、刪除可復原

### IG 所有人被併成同一個（最嚴重）

`isGroupFlag` 把 `!convTitle.isNullOrBlank()` 也當成群組條件。
**Instagram 連一對一私訊都會帶 `conversationTitle`**，於是每則 IG 私訊都被判成群組，
`senderName` 一律取 `convTitle`（使用者自己的帳號），真正的對話對象被塞進 `subSender`。
畫面上就變成所有 IG 聯絡人合併為一人、底下掛著「群組發言排行」。

修法：群組判定只信 `android.isGroupConversation` 官方旗標，或「訊息陣列裡有兩位以上不同發言人」。

### 自己發的訊息被算成收到的訊息

`Notification.MessagingStyle` 規格：**`sender` 為 null 代表該則訊息由使用者本人發出**。
舊版把這些全部當成對方傳來的訊息計入，訊息數虛胖，`subSender` 還會出現使用者自己的名字。

修法：過濾掉 `sender == null` 以及 `sender == android.selfDisplayName` 的訊息。
若整則通知都是自己發的，直接不計入。

### 除了 LINE 都偵測不到停留時長

`extractChatName()` 比對的是**寫死的完整 view id**。Threads（`com.instagram.barcelona`）
在清單裡根本沒有任何 id，IG 的 id 也早已隨改版失效 → 永遠回傳 null → 立刻結算 → 0 秒。

修法：改為三層策略，且只走訪節點樹一次
1. 以 **view id 後綴**比對（`header_title` / `thread_title` / `action_bar_title`…），
   不寫死套件前綴，App 改版換 id 前綴仍然抓得到
2. 找不到就取畫面**頂端 20% 內最上方的文字**，排除時鐘、純數字、已知非標題字樣
3. 仍需偵測到輸入框才算真的在聊天室（通話畫面除外）

### LINE 停留時間漏算

舊版只要有**一次**抓不到標題就立刻 `leaveChat()` 結算。畫面重繪時抓不到是常態，
於是一段連續停留被切成大量碎片，而每個碎片不足 1 秒就被 `elapsed <= 0` 丟掉。

修法：
- **容錯**：連續 3 次抓不到才視為離開
- **接續**：離開後 25 秒內回到同一個聊天室，接續累加而不是重開一段
- **暫存**：離開時先進暫存區並排程結算，期間切回來可續算；關螢幕或服務停止則立即結算
- 內容變更事件節流從 1200ms 收緊到 800ms，減少漏抓

### 刪除可復原

所有破壞性操作（一鍵清除垃圾聯絡人、多選刪除、清除今日／本週／指定日期／全部、
清理異常紀錄、刪除紀錄）執行前，都會先把完整資料快照存到 App 內部空間。
設定頁「資料管理」會出現「可復原上一次刪除」與復原按鈕。

> 實作注意：快照的狀態必須**同步**擷取。呼叫端會在函式回傳後立刻改資料，
> 若把讀取也丟進背景協程，快照會拍到已刪除後的狀態，復原就失效。
> 現在是同步抓住不可變引用，序列化與寫檔才交給背景。

### 逐筆檢視／勾選刪除紀錄

設定頁 →「逐筆檢視／勾選刪除紀錄」。顯示最新 400 筆，可依對象或平台搜尋，
每列顯示時間、平台、停留時長／字數／通話狀態／群組發言者，勾選後批次刪除（可復原）。

### 聯絡人分軟體

聯絡人頁新增平台晶片列（全平台／LINE／Instagram／Threads…），
每張聯絡人卡片也會標示該聯絡人出現過的來源 App。

### 一週起始日

「單週」的日期一律顯示實際區間（例：`本週 8/25 - 8/31`），
方便直接核對起始日設定有沒有生效。另修正「進階資料管理」的日曆
沒有吃到一週起始日設定的問題。
